OpenClaw里为何会每一轮都会把所有上下文发送？

momo · 发布：2026-03-12T07:07:59+00:00 · 更新：2026-03-12T07:53:47+00:00

查看知乎原文

我确认了一下，OpenClaw 默认确实是“每一轮 run 都重新组装并发送当前上下文给模型”，而不是只发“新增的那一句”。官方文档对 context 的定义就是：“一次 run 里 OpenClaw 发送给模型的全部内容”，其中包括系统提示词、当前 session 的对话历史，以及工具调用/工具结果/附件等。(OpenClaw)

更直接一点说，OpenClaw 的工作方式接近：

  • 从 gateway 上保存的 session transcript 里取历史；
  • 再加上系统提示词、工具 schema、注入文件等；
  • 拼成这一次请求的完整 context；
  • 发给模型。 官方文档还写到，session transcript 保存在 gateway 主机上，JSONL transcript 可以直接查看；而且 /compact 的作用正是把旧历史压缩成摘要，给未来请求继续使用，这也侧面说明后续请求本来就是要再次带上这些上下文的。(OpenClaw)

你问“为何会每一轮都把所有上下文发送”，原因基本可以归纳成这几个：

第一，OpenClaw 自己维护 session，但模型调用这一层仍然按“本轮所需完整上下文”来运行。 OpenClaw 文档把 context 明确描述成 “everything OpenClaw sends to the model for a run”，这说明它的抽象就是 run-based prompt assembly，不是“给模型端开一个永久驻留会话缓冲区”。(OpenClaw)

第二，工具调用循环也会重复带上下文。 社区 issue 里有人专门问过：如果 session 很长，再加一个超大的工具输出，后续 1–20 次 tool loop 会不会每次都把“完整历史 + 巨大工具输出”再发一遍？回答是 yes。虽然这是 GitHub issue 里的描述，不算正式设计文档，但和官方 context/compaction 文档是吻合的。(GitHub)

第三，这也是它为什么需要 compaction 和 pruning。 如果不是每轮重带上下文，那就没必要专门提供：

  • /compact：把旧历史压成摘要；
  • contextPruning：在发给 LLM 前，修剪旧的 tool result。 官方配置文档明确说 contextPruning 是 “before sending to the LLM” 对内存中的上下文做裁剪，而且不会修改磁盘上的 session history。这几乎就是明说：磁盘上保留全历史，但每轮发送前会按规则裁剪/压缩后再发。(OpenClaw)

所以结论可以说得很明确：

是的，OpenClaw 默认就是每一轮都重新发送“当前要用的完整上下文”，而不是只 append 新消息给模型端一个已驻留的 session。 只是这个“完整上下文”不一定永远是原始全量历史，因为它可能会经过：

  • compaction：旧对话变摘要
  • contextPruning：旧工具输出被裁剪或清空
  • historyLimit / inbound history 包装：某些 channel 只带有限历史

但本质上仍然是每轮重建 prompt 再发送。(OpenClaw)

再补一个你可能关心的点：

OpenClaw 之所以会显得“很笨重”，不是因为它不会存 session；它是会存 session 的。问题在于，session 存储 ≠ 模型端持久驻留 KV cache。OpenClaw 把 transcript 存在 gateway 本地，下一轮再加载、拼接、发送；这和你前面设想的“后端给每个 session 固定留一块 128K 上下文空间，然后只 append”不是一回事。(OpenClaw)
