You've built a chatbot. Maybe you've wired up a ReAct loop with a few tools. It works for demos. Then you try to build something production-grade, and the wheels come off: the model forgets what it did three steps ago, tool calls fail silently, and context windows fill up with garbage.你已经搭建了一个聊天机器人。或许你还将 ReAct 循环与几个工具连接了起来。这个方案在演示场景下能正常运行，但当你试图打造生产级别的应用时，问题就接踵而至了：模型会忘记前三步的操作，工具调用会无声地失败，上下文窗口还会被无用信息填满。

The problem isn't your model. It's everything around your model.问题不在于你的模型，而在于模型周边的一切。

LangChain proved this when they changed only the infrastructure wrapping their LLM (same model, same weights) and jumped from outside the top 30 to rank 5 on TerminalBench 2.0. A separate research project hit a 76.4% pass rate by having an LLM optimize the infrastructure itself, surpassing hand-designed systems.LangChain 就证明了这一点：他们仅修改了封装其大语言模型（LLM）的基础设施（模型本身、权重均未改变），就在 TerminalBench 2.0 上从第 30 名开外跃升至第 5 名。另有一项独立研究项目让大语言模型自行优化基础设施，最终通过率达到 76.4%，超过了人工设计的系统。

That infrastructure has a name now: the agent harness.如今，这套基础设施有了一个名字：智能体框架。

What Is the Agent Harness? 什么是智能体框架？

The term was formalized in early 2026, but the concept existed long before. The harness is the complete software infrastructure wrapping an LLM: orchestration loop, tools, memory, context management, state persistence, error handling, and guardrails. Anthropic's Claude Code documentation puts it simply: the SDK is "the agent harness that powers Claude Code." OpenAI's Codex team uses the same framing, explicitly equating the terms "agent" and "harness" to refer to the non-model infrastructure that makes the LLM useful.这一术语于2026年初正式确立，但其概念早已存在。所谓“框架”是指包裹大语言模型（LLM）的完整软件基础设施，包括编排循环、工具、记忆、上下文管理、状态持久化、错误处理以及安全护栏。Anthropic 公司的 Claude Code 文档对此的表述十分简洁：该软件开发工具包（SDK）是“为 Claude Code 提供支持的智能体框架”。OpenAI 的 Codex 团队也采用了这一表述，明确将“智能体”与“框架”这两个术语等同，指代那些让大语言模型具备实用价值的非模型基础设施。

I really liked the canonical formula, from LangChain's Vivek Trivedy: "If you're not the model, you're the harness."我真的很喜欢朗Chain的维韦克·特里维迪提出的那句经典表述：“如果你不是模型，那你就是配套工具。”

Here's the distinction that trips people up. The "agent" is the emergent behavior: the goal-directed, tool-using, self-correcting entity the user interacts with. The harness is the machinery producing that behavior. When someone says "I built an agent," they mean they built a harness and pointed it at a model.这就是让人容易混淆的区别。“智能体”是一种涌现行为：是用户与之交互的、有目标导向、会使用工具、能自我修正的实体。而“框架”是催生这种行为的底层机制。当有人说“我打造了一个智能体”时，他们的意思是搭建了一个框架，并将其对接在了一个模型上。

Beren Millidge made this analogy precise in his 2023 essay "Scaffolded LLMs as Natural Language Computers.作为自然语言计算机的脚手架式大语言模型
" A raw LLM is a CPU with no RAM, no disk, and no I/O. The context window serves as RAM (fast but limited). External databases function as disk storage (large but slow). Tool integrations act as device drivers. The harness is the operating system. As Millidge wrote: "We have reinvented the Von Neumann architecture" because it's a natural abstraction for any computing system.贝伦·米利奇在其2023年的文章《作为自然语言计算机的脚手架式大语言模型》中精准阐述了这一类比。原始的大语言模型就像是一台没有随机存取存储器、没有硬盘、也没有输入/输出功能的中央处理器。上下文窗口相当于随机存取存储器（速度快但容量有限）；外部数据库充当着硬盘存储的角色（容量大但速度慢）；工具集成则扮演着设备驱动程序的作用；而整体框架就如同操作系统。正如米利奇所写的那样：“我们重新发明了冯·诺依曼架构”，因为对于任何计算系统而言，这都是一种自然而然的抽象概念。

Three Levels of Engineering 工程的三个层级

Three concentric levels of engineering surround the model:模型周围有三个同心的工程层级：

  • Prompt engineering crafts the instructions the model receives.提示工程为模型设计其所接收的指令。
  • Context engineering manages what the model sees and when.上下文工程管理模型所看到的内容以及查看的时机。
  • Harness engineering encompasses both, plus the entire application infrastructure: tool orchestration, state persistence, error recovery, verification loops, safety enforcement, and lifecycle management.治理工程涵盖了这两者，再加上整个应用基础设施：工具编排、状态持久化、错误恢复、验证循环、安全执行以及生命周期管理。

The harness is not a wrapper around a prompt. It is the complete system that makes autonomous agent behavior possible.该框架并非提示词的包装器，而是实现自主智能体行为的完整系统。

The 12 Components of a Production Harness生产环境代理框架的12个组成部分

Synthesizing across Anthropic, OpenAI, LangChain, and the broader practitioner community, a production agent harness has twelve distinct components. Let's walk through each one.综合Anthropic、OpenAI、LangChain以及更广泛的从业者社区的经验，一个生产级智能体框架包含十二个不同的组件。我们来逐一梳理。

1. The Orchestration Loop 1. 编排循环

This is the heartbeat. It implements the Thought-Action-Observation (TAO) cycle, also called the ReAct loop. The loop runs: assemble prompt, call LLM, parse output, execute any tool calls, feed results back, repeat until done.这就是核心循环。它实现了思想-行动-观察（TAO）循环，也被称为ReAct循环。该循环的运行流程为：组装提示词、调用大语言模型、解析输出、执行所有工具调用、反馈结果，如此循环直至任务完成。

Mechanically, it's often just a while loop. The complexity lives in everything the loop manages, not the loop itself. Anthropic describes their runtime as a "dumb loop" where all intelligence lives in the model. The harness just manages turns.从机械层面来说，它通常就是一个 while 循环。复杂之处在于循环所管理的所有内容，而非循环本身。Anthropic 将其运行时描述为一个“无脑循环”，所有智能都存在于模型中。框架仅负责管理交互轮次。

2. Tools 2. 工具

Tools are the agent's hands. They're defined as schemas (name, description, parameter types) injected into the LLM's context so the model knows what's available. The tool layer handles registration, schema validation, argument extraction, sandboxed execution, result capture, and formatting results back into LLM-readable observations.工具是智能体的“双手”。它们被定义为模式（名称、描述、参数类型）并注入到大语言模型的上下文之中，以便模型了解可用的工具。工具层负责处理注册、模式验证、参数提取、沙箱执行、结果捕获，以及将结果格式化为大语言模型可读取的观测信息。

Claude Code provides tools across six categories: file operations, search, execution, web access, code intelligence, and subagent spawning. OpenAI's Agents SDK supports function tools (via @function_tool
), hosted tools (WebSearch, CodeInterpreter, FileSearch), and MCP server tools.Claude Code 提供六大类工具：文件操作、搜索、执行、网络访问、代码智能以及子代理生成。OpenAI 的 Agents SDK 支持函数工具（通过 @function_tool）、托管工具（网络搜索、代码解释器、文件搜索）和 MCP 服务器工具。

3. Memory 3. 记忆

Memory operates at multiple timescales. Short-term memory is conversation history within a single session. Long-term memory persists across sessions: Anthropic uses CLAUDE.md
project files and auto-generated MEMORY.md
files; LangGraph uses namespace-organized JSON Stores; OpenAI supports Sessions backed by SQLite or Redis.记忆以多种时间尺度运行。短期记忆是单次会话内的对话历史。长期记忆可跨会话持续存在：Anthropic 使用 CLAUDE.md 项目文件和自动生成的 MEMORY.md 文件；LangGraph 使用按命名空间组织的 JSON 存储；OpenAI 支持由 SQLite 或 Redis 提供支持的会话。

Claude Code implements a three-tier hierarchy: a lightweight index (~150 characters per entry, always loaded), detailed topic files pulled in on demand, and raw transcripts accessed via search only. A critical design principle: the agent treats its own memory as a "hint" and verifies against actual state before acting.Claude Code 实现了三层层级结构：轻量级索引（每个条目约150个字符，始终加载）、按需加载的详细主题文件，以及仅通过搜索访问的原始转录文本。核心设计原则为：智能体将自身记忆视为“提示信息”，并在执行操作前依据实际状态进行验证。

4. Context Management 4. 上下文管理

This is where many agents fail silently. The core problem is context rot: model performance degrades 30%+ when key content falls in mid-window positions (Chroma research, corroborated by Stanford's "Lost in the Middle" finding). Even million-token windows suffer from instruction-following degradation as context grows.这就是许多智能体悄无声息地出现问题的地方。核心问题是上下文衰减：当关键内容处于上下文窗口的中间位置时，模型性能会下降30%以上（这是Chroma的研究结论，也得到了斯坦福大学“迷失在中间”研究发现的佐证）。即便是拥有百万token上下文窗口的模型，随着上下文规模的扩大，指令遵循能力也会出现衰减。

Production strategies include: 生产策略包括：

  • Compaction: summarizing conversation history when approaching limits (Claude Code preserves architectural decisions and unresolved bugs while discarding redundant tool outputs)压缩：接近限制时汇总对话历史（Claude Code 保留架构决策和未解决的 bug，同时丢弃冗余的工具输出）
  • Observation masking: JetBrains' Junie hides old tool outputs while keeping tool calls visible观察屏蔽：JetBrains 的 Junie 会隐藏旧的工具输出，同时保留工具调用的可见性
  • Just-in-time retrieval: maintaining lightweight identifiers and loading data dynamically (Claude Code uses grep, glob, head, tail rather than loading full files)即时检索：维护轻量级标识符并动态加载数据（Claude Code 使用 grep、glob、head、tail 命令，而非加载完整文件）
  • Sub-agent delegation: each subagent explores extensively but returns only 1,000 to 2,000 token condensed summaries子智能体委派：每个子智能体进行广泛探索，但仅返回1000至2000个token的精简摘要

Anthropic's context engineering guide states the goal: find the smallest possible set of high-signal tokens that maximize likelihood of the desired outcome.Anthropic 的上下文工程指南指出了目标：找到尽可能小的高信号标记集合，以最大化期望结果的可能性。

5. Prompt Construction 5. 提示词构建

This assembles what the model actually sees at each step. It's hierarchical: system prompt, tool definitions, memory files, conversation history, and the current user message.这集合了模型在每个步骤中实际看到的内容。它是分层的：系统提示、工具定义、内存文件、对话历史和当前用户消息。

OpenAI's Codex uses a strict priority stack: server-controlled system message (highest priority), tool definitions, developer instructions, user instructions (cascading AGENTS.md
files, 32 KiB limit), then conversation history.OpenAI 的 Codex 使用严格的优先级栈：服务器控制的系统消息（最高优先级）、工具定义、开发者指令、用户指令（级联的 AGENTS.md 文件，32 千字节限制），然后是对话历史。

6. Output Parsing 6. 输出解析

Modern harnesses rely on native tool calling, where the model returns structured tool_calls objects rather than free-text that must be parsed. The harness checks: are there tool calls? Execute them and loop. No tool calls? That's the final answer.现代测试框架依赖原生工具调用，模型会返回结构化的 tool_calls 对象，而非需要解析的自由文本。测试框架会进行如下检查：是否存在工具调用？若有则执行并循环处理；若无，则输出最终答案。

For structured outputs, both OpenAI and LangChain support schema-constrained responses via Pydantic models. Legacy approaches like RetryWithErrorOutputParser (which feeds the original prompt, the failed completion, and the parsing error back to the model) remain available for edge cases.对于结构化输出，OpenAI 和 LangChain 均支持通过 Pydantic 模型生成受模式约束的响应。像 RetryWithErrorOutputParser 这类传统方法（将原始提示词、失败的补全结果以及解析错误反馈给模型），在边缘场景下依然可用。

7. State Management 7. 状态管理

LangGraph models state as typed dictionaries flowing through graph nodes, with reducers merging updates. Checkpointing happens at super-step boundaries, enabling resume after interruptions and time-travel debugging. OpenAI offers four mutually exclusive strategies: application memory, SDK sessions, server-side Conversations API, or lightweight previous_response_id chaining. Claude Code takes a different approach: git commits as checkpoints and progress files as structured scratchpads.LangGraph 将状态建模为在图节点间流动的类型化字典，并通过归约器合并更新。检查点机制设置在超步骤边界处，支持中断后恢复与时间旅行调试。OpenAI 提供四种互斥策略：应用内存、SDK 会话、服务端对话 API，或轻量级的 previous_response_id 链式调用。Claude Code 采用不同思路：以 Git 提交作为检查点，以进度文件作为结构化的临时工作区。

8. Error Handling 8. 错误处理

Here's why this matters: a 10-step process with 99% per-step success still has only ~90.4% end-to-end success. Errors compound fast.原因如下：一个包含10个步骤、每个步骤成功率为99%的流程，其整体端到端成功率仅约为90.4%。错误会迅速累积。

LangGraph distinguishes four error types: transient (retry with backoff), LLM-recoverable (return error as ToolMessage so the model can adjust), user-fixable (interrupt for human input), and unexpected (bubble up for debugging). Anthropic catches failures within tool handlers and returns them as error results to keep the loop running. Stripe's production harness caps retry attempts at two.LangGraph 区分了四种错误类型：暂时性错误（带退避重试）、大语言模型可恢复错误（将错误作为 ToolMessage 返回以便模型调整）、用户可修复错误（中断以获取人工输入）以及意外错误（向上冒泡以进行调试）。Anthropic 会捕获工具处理程序中的故障并将其作为错误结果返回，以保持循环持续运行。Stripe 的生产测试工具将重试次数限制为两次。

9. Guardrails and Safety 9. 护栏与安全

OpenAI's SDK implements three levels: input guardrails (run on first agent), output guardrails (run on final output), and tool guardrails (run on every tool invocation). A "tripwire" mechanism halts the agent immediately when triggered.OpenAI 的软件开发工具包（SDK）实现了三个层级：输入防护栏（在首个智能体上运行）、输出防护栏（在最终输出时运行）以及工具防护栏（在每次工具调用时运行）。当“触发线”机制被触发时，会立即停止智能体的运行。

Anthropic separates permission enforcement from model reasoning architecturally. The model decides what to attempt; the tool system decides what's allowed. Claude Code gates ~40 discrete tool capabilities independently, with three stages: trust establishment at project load, permission check before each tool call, and explicit user confirmation for high-risk operations.Anthropic 在架构上将权限执行与模型推理分离开。模型决定要尝试执行什么操作；工具系统决定允许执行什么操作。Claude 对约 40 种独立的工具功能进行代码级权限控制，包含三个阶段：项目加载时建立信任、每次调用工具前进行权限检查、以及针对高风险操作获取用户的明确确认。

10. Verification Loops 10. 验证循环

This is what separates toy demos from production agents. Anthropic recommends three approaches: rules-based feedback (tests, linters, type checkers), visual feedback (screenshots via Playwright for UI tasks), and LLM-as-judge (a separate subagent evaluates output).这正是玩具级演示与生产级智能体的区别所在。Anthropic 推荐了三种方法：基于规则的反馈（测试、代码检查工具、类型检查器）、可视化反馈（通过 Playwright 获取 UI 任务的截图）以及大模型作为评判者（由独立的子智能体评估输出结果）。

Boris Cherny, creator of Claude Code, noted that giving the model a way to verify its work improves quality by 2 to 3x.Claude Code 的创作者鲍里斯·切尔尼指出，为模型提供一种验证其工作成果的方式，可将质量提升2至3倍。

11. Subagent Orchestration 11. 子智能体编排

Claude Code supports three execution models: Fork (byte-identical copy of parent context), Teammate (separate terminal pane with file-based mailbox communication), and Worktree (own git worktree, isolated branch per agent). OpenAI's SDK supports agents-as-tools (specialist handles bounded subtask) and handoffs (specialist takes full control). LangGraph implements subagents as nested state graphs.Claude Code 支持三种执行模型：Fork（父上下文的字节完全相同副本）、Teammate（带有基于文件的邮箱通信的独立终端窗格）和 Worktree（拥有独立的 git 工作树，每个智能体对应一个独立分支）。OpenAI 的 SDK 支持智能体即工具（专业智能体处理有限子任务）和交接（专业智能体完全接管控制权）。LangGraph 将子智能体实现为嵌套状态图。

The Loop in Motion: A Step-by-Step Walkthrough动态循环：分步详解

Now that you know the components, let's trace how they work together in a single cycle.既然你已经了解了各个组件，让我们来追踪它们在一个完整周期内如何协同工作。

Step 1 (Prompt Assembly): The harness constructs the full input: system prompt + tool schemas + memory files + conversation history + current user message. Important context is positioned at the beginning and end of the prompt (the "Lost in the Middle" finding).第1步（提示组装）：线束构建完整的输入：系统提示+工具模式+内存文件+对话历史+当前用户消息。重要上下文位于提示的开头和结尾（“迷失在中间”发现）。

Step 2 (LLM Inference): The assembled prompt goes to the model API. The model generates output tokens: text, tool call requests, or both.步骤2（大模型推理）：组装好的提示词会被发送至模型API。模型会生成输出标记：文本、工具调用请求，或两者兼具。

Step 3 (Output Classification): If the model produced text with no tool calls, the loop ends. If it requested tool calls, proceed to execution. If a handoff was requested, update the current agent and restart.步骤3（输出分类）：如果模型生成的文本未调用任何工具，则循环结束。如果模型请求调用工具，则执行后续步骤。如果请求切换代理，则更新当前代理并重新启动流程。

Step 4 (Tool Execution): For each tool call, the harness validates arguments, checks permissions, executes in a sandboxed environment, and captures results. Read-only operations can run concurrently; mutating operations run serially.步骤4（工具执行）：针对每次工具调用，测试工具会验证参数、检查权限、在沙箱环境中执行并捕获结果。只读操作可并发运行；修改操作需串行执行。

Step 5 (Result Packaging): Tool results are formatted as LLM-readable messages. Errors are caught and returned as error results so the model can self-correct.步骤5（结果封装）：工具结果被格式化为可供大模型读取的消息。错误会被捕获并作为错误结果返回，以便大模型能够进行自我修正。

Step 6 (Context Update): Results are appended to conversation history. If approaching the context window limit, the harness triggers compaction.步骤6（上下文更新）：结果会附加到对话历史中。如果接近上下文窗口限制，工具会触发压缩操作。

Step 7 (Loop): Return to Step 1. Repeat until termination.步骤7（循环）：返回步骤1，重复执行直至终止。

Termination conditions are layered: the model produces a response with no tool calls, maximum turn limit is exceeded, token budget is exhausted, a guardrail tripwire fires, the user interrupts, or a safety refusal is returned. A simple question might take 1 to 2 turns. A complex refactoring task can chain dozens of tool calls across many turns.终止条件是分层设置的：模型生成不包含工具调用的回复、超过最大轮次限制、令牌预算耗尽、触发护栏触发条件、用户中断或返回安全拒绝。一个简单的问题可能需要1到2轮。一项复杂的重构任务可能会在多轮中串联数十次工具调用。

For long-running tasks spanning multiple context windows, Anthropic developed a two-phase "Ralph Loop" pattern对于跨越多个上下文窗口的长期运行任务，Anthropic 开发了一种两阶段的“Ralph Loop”模式
: an Initializer Agent sets up the environment (init script, progress file, feature list, initial git commit), then a Coding Agent in every subsequent session reads git logs and progress files to orient itself, picks the highest-priority incomplete feature, works on it, commits, and writes summaries. The filesystem provides continuity across context windows.对于跨越多个上下文窗口的长期任务，Anthropic 开发了一种两阶段的“拉尔夫循环”模式：初始化智能体设置环境（初始化脚本、进度文件、功能列表、初始 git 提交），然后在后续每个会话中的编码智能体读取 git 日志和进度文件以明确自身状态，选择优先级最高的未完成功能，开展开发工作、提交代码并撰写总结。文件系统为跨上下文窗口的任务提供了连续性。

How Real Frameworks Implement the Pattern 实际框架如何实现该模式


Anthropic's Claude Agent SDK exposes the harness through a single query() function that creates the agentic loop and returns an async iterator streaming messages. The runtime is a "dumb loop." All intelligence lives in the model. Claude Code uses a Gather-Act-Verify cycle: gather context (search files, read code), take action (edit files, run commands), verify results (run tests, check output), repeat.Anthropic 的 Claude Agent SDK 通过单个 query() 函数暴露该框架，该函数会创建智能体循环并返回一个流式传输消息的异步迭代器。其运行时是一个“简单循环”，所有智能都存在于模型中。Claude Code 采用“收集-执行-验证”循环：收集上下文（搜索文件、读取代码）、执行操作（编辑文件、运行命令）、验证结果（运行测试、检查输出），然后重复这一过程。

OpenAI's Agents SDK implements the harness through the Runner class with three modes: async, sync, and streamed. The SDK is "code-first": workflow logic is expressed in native Python rather than graph DSLs. The Codex harness extends this with a three-layer architecture: Codex Core (agent code + runtime), App Server (bidirectional JSON-RPC API), and client surfaces (CLI, VS Code, web app). All surfaces share the same harness, which is why "Codex models feel better on Codex surfaces than a generic chat window."OpenAI的Agents SDK通过Runner类实现了测试框架，包含异步、同步和流式三种模式。该SDK采用“代码优先”设计：工作流逻辑通过原生Python编写，而非图形化领域特定语言。Codex测试框架在此基础上扩展了三层架构：Codex核心（智能体代码+运行时）、应用服务器（双向JSON-RPC API）和客户端界面（命令行界面、VS Code、网页应用）。所有客户端界面共享同一套测试框架，这也是“Codex模型在Codex界面上的表现比通用聊天窗口更出色”的原因。

LangGraph models the harness as an explicit state graph. Two nodes (llm_call and tool_node) connected by a conditional edge: if tool calls present, route to tool_node; if absent, route to END. LangGraph evolved from LangChain's AgentExecutor, which was deprecated in v0.2 because it was hard to extend and lacked multi-agent support. LangChain's Deep Agents explicitly use the term "agent harness": built-in tools, planning (write_todos tool), file systems for context management, subagent spawning, and persistent memory.LangGraph 将工具框架建模为显式状态图。两个节点（llm_call 和 tool_node）通过条件边连接：若存在工具调用，则路由至 tool_node；若不存在，则路由至 END。LangGraph 脱胎于 LangChain 的 AgentExecutor，该组件在 0.2 版本中被弃用，原因是其扩展性差且不支持多智能体。LangChain 的深度智能体明确使用“智能体工具框架”这一术语：包含内置工具、规划（write_todos 工具）、用于上下文管理的文件系统、子智能体生成以及持久化内存。

CrewAI implements a role-based multi-agent architecture: Agent (the harness around the LLM, defined by role, goal, backstory, and tools), Task (the unit of work), and Crew (the collection of agents). CrewAI's Flows layer adds a "deterministic backbone with intelligence where it matters," managing routing and validation while Crews handle autonomous collaboration.CrewAI 实现了一种基于角色的多智能体架构：智能体（围绕大语言模型的框架，由角色、目标、背景和工具定义）、任务（工作单元）和团队（智能体的集合）。CrewAI 的流程层增添了“在关键位置融入智能的确定性主干”，在团队开展自主协作的同时，负责管理路由和验证。

AutoGen (evolving into Microsoft Agent Framework) pioneered conversation-driven orchestration. Its three-layer architecture (Core, AgentChat, Extensions) supports five orchestration patterns: sequential, concurrent (fan-out/fan-in), group chat, handoff, and magentic (a manager agent maintains a dynamic task ledger coordinating specialists).AutoGen（正发展为微软智能体框架）开创了对话驱动的编排技术。其三层架构（核心层、智能体聊天层、扩展层）支持五种编排模式：顺序模式、并发模式（扇出/扇入）、群聊模式、切换模式和磁模式（由管理智能体维护动态任务分类账，协调专业智能体）。

The Scaffolding Metaphor 脚手架隐喻

The scaffolding metaphor isn't decorative. It's precise. Construction scaffolding is temporary infrastructure that enables workers to build a structure they couldn't reach otherwise. It doesn't do the construction. But without it, workers can't reach the upper floors.脚手架这个比喻并非装饰性的，而是精准的。建筑用脚手架是一种临时基础设施，能让工人搭建出他们原本够不着的建筑结构。它不负责施工，但没有它，工人就无法到达上层楼层。


The key insight: scaffolding is removed when the building is complete. As models improve, harness complexity should decrease. Manus s rebuilt five times in six months, each rewrite removing complexity. Complex tool definitions became general shell execution. "Management agents" became simple structured handoffs.核心洞见：建筑完工后脚手架便会拆除。随着模型的不断优化，驾驭复杂性的难度应当随之降低。曼努斯系统在六个月内被重构了五次，每一次重构都在剔除复杂性。复杂的工具定义演变为通用的外壳执行。“管理智能体”则变成了简单的结构化交接。

This points to the co-evolution principle: models are now post-trained with specific harnesses in the loop. Claude Code's model learned to use the specific harness it was trained with. Changing tool implementaions can degrade performance because of this tight coupling.这指向了共同进化原则：如今的模型在训练后会结合特定的工具框架进行微调。Claude Code 的模型学会了使用其训练时所配套的特定工具框架。由于这种紧密的耦合关系，更换工具的实现方式可能会导致模型性能下降。

The "future-proofing test" for harness design: if performance scales up with more powerful models without adding harness complexity, the design is sound.用于 harness 设计的“前瞻性测试”：如果在不增加 harness 复杂度的情况下，性能可随更强大的模型提升，那么该设计就是合理的。




Seven Decisions That Define Every Harness定义每个线束的七大决策

Every harness architect faces seven choices:每位线束架构师都面临七个选择：





  1. Single-agent vs. multi-agent. Both Anthropic and OpenAI say: maximize a single agent first. Multi-agent systems add overhead (extra LLM calls for routing, context loss during handoffs). Split only when tool overload exceeds ~10 overlapping tools or clearly separate task domains exist.单智能体与多智能体。Anthropic 和 OpenAI 均表示：应优先最大化单个智能体的性能。多智能体系统会增加额外开销（路由需要额外调用大语言模型、智能体交接时会出现上下文丢失）。仅当工具负载超过约 10 个重叠工具，或存在明确的任务域划分时，再拆分为多智能体。
  2. ReAct vs. plan-and-execute. ReAct interleaves reasoning and action at every step (flexible but higher per-step cost). Plan-and-execute separates planning from execution. LLMCompiler reports a 3.6x speedup over sequential ReAct.ReAct 与规划-执行模式对比。ReAct 在每一步都交错进行推理和行动（灵活但每一步的成本更高）。规划-执行模式将规划与执行分离开来。LLMCompiler 报告称其比串行 ReAct 实现了 3.6 倍的速度提升。
  3. Context window management strategy. Five production approaches: time-based clearing, conversation summarization, observation masking, structured note-taking, and sub-agent delegation. ACON research showed 26 to 54% token reduction while preserving 95%+ accuracy by prioritizing reasoning traces over raw tool outputs.上下文窗口管理策略。五种生成式处理方法：基于时间的清理、对话摘要生成、观察屏蔽、结构化笔记记录和子代理委托。ACON 研究表明，通过优先考虑推理轨迹而非原始工具输出，可将令牌减少 26% 至 54%，同时保持 95% 以上的准确率。
  4. Verification loop design. Computational verification (tests, linters) provides deterministic ground truth. Inferential verification (LLM-as-judge) catches semantic issues but adds latency. Martin Fowler's Thoughtworks team frames this as guides (feedforward, steer before action) versus sensors (feedback, observe after action).验证循环设计。计算验证（测试、代码检查工具）可提供确定的基本事实。推理验证（大模型作为评判者）能发现语义问题但会增加延迟。马丁·福勒所在的 Thoughtworks 团队将此定义为引导机制（前馈、行动前引导）与感知机制（反馈、行动后观察）的对比。
  5. Permission and safety architecture. Permissive (fast but risky, auto-approve most actions) versus restrictive (safe but slow, require approval for each action). The choice depends on deployment context.权限与安全架构。宽松型（速度快但风险高，自动批准大多数操作）与严格型（安全但速度慢，每项操作均需审批）。选择取决于部署场景。
  6. Tool scoping strategy. More tools often means worse performance. Vercel removed 80% of tools from v0 and got better results. Claude Code achieves 95% context reduction via lazy loading. The principle: expose the minimum tool set needed for the current step.工具范围界定策略。工具越多往往意味着性能越差。Vercel 在 v0 版本中移除了 80% 的工具，反而取得了更好的效果。Claude Code 通过懒加载实现了 95% 的上下文缩减。其核心原则是：为当前步骤暴露所需的最小工具集。
  7. Harness thickness. How much logic lives in the harness versus the model. Anthropic bets on thin harnesses and model improvement. Graph-based frameworks bet on explicit control. Anthropic regularly deletes planning steps from Claude Code's harness as new model versions internalize that capability. harness 厚度。harness 与模型中包含的逻辑占比各为多少。Anthropic 倾向于轻量化 harness 并优化模型。基于图的框架则注重显式控制。随着新版模型掌握相关能力，Anthropic 会定期从 Claude Code 的 harness 中删除规划步骤。

The Harness Is the Product 框架即产品

Two products using identical models can have wildly different performance based solely on harness design. The TerminalBench evidence is clear: changing only the harness moved agents by 20+ ranking positions.两款采用相同模型的产品，仅凭线束设计的不同，性能就可能天差地别。TerminalBench 的证据十分明确：仅更换线束，就使智能体的排名提升了20多个位次。

The harness is not a solved problem or a commodity layer. It's where the hard engineering lives: managing context as a scarce resource, designing verification loops that catch failures before they compound, building memory systems that provide continuity without hallucination, and making architectural bets about how much scaffolding to build versus how much to leave to the model.这套框架并非一个已解决的问题，也不是一层通用的基础组件。它承载着核心的工程难点：将上下文视为稀缺资源进行管理，设计验证循环以在故障扩大前及时发现问题，构建既能保持连续性又不会产生幻觉的记忆系统，以及在架构层面做出权衡——确定需要搭建多少支撑框架，又有多少可以交由模型自主完成。

The field is moving toward thinner harnesses as models improve. But the harness itself isn't going away. Even the most capable model needs something to manage its context window, execute its tool calls, persist its state, and verify its work.随着模型不断优化，该领域正朝着更轻量化的“控制框架”发展。但控制框架本身并不会消失。即便是性能最强大的模型，也需要借助它来管理上下文窗口、执行工具调用、持久化状态并验证结果。

The next time your agent fails, don't blame the model. Look at the harness.下次你的智能体出问题时，别去怪模型。去看看测试框架。
